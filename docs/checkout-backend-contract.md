# Commandes FORNO — Supabase / Sites

## État et architecture

Astro reste le framework principal ; aucun composant React ni SDK navigateur Supabase. L’adapter officiel Cloudflare rend uniquement les routes API à la demande (`prerender=false`). Les pages publiques et le tunnel sont prérendus, avec leurs images optimisées à la compilation. Le build assemble un Worker ESM `dist/server/index.js` et les ressources `dist/client` pour l’hébergement Sites existant. `session:false` évite un binding KV inutile. Aucun changement de design des sections publiques.

La connexion réelle n’est **pas configurée** à la livraison : aucun secret Supabase ou Turnstile n’était présent. Les API renvoient HTTP 503 `NOT_CONFIGURED`, le tunnel bloque l’envoi et n’affiche aucun faux succès. Les tests locaux utilisent une base PostgreSQL PGlite isolée et des identifiants de test uniquement.

## Configuration et déploiement

1. Créer ou sélectionner le véritable projet Supabase. Vérifier la région et les accès métier. Appliquer dans l’ordre les migrations `supabase/migrations/` avec Supabase CLI (`supabase db push`) ou l’éditeur SQL. Conserver la version des migrations. Pour SQL Editor, utiliser le lot suivi décrit dans `docs/supabase-forno-pizza-setup.md`. Le durcissement complémentaire laisse le cron inactif jusqu’à validation ; il devra être activé et contrôlé avant toute ouverture réelle.
2. Le catalogue initial provient de `src/data/pizzas.ts`. `node scripts/prepare-order-data.mjs catalogue` permet de contrôler le SQL de référence ; la migration catalogue existante n’écrase jamais des prix en production. Les prix sont des entiers en centimes. **Montagnarde et Norvégienne sont indisponibles tant que leurs tarifs ne sont pas vérifiés.** Valider ensuite en base prix et disponibilité ; le catalogue statique public doit être mis à jour et redéployé lors d’un changement de recette/prix.
3. Générer des services datés depuis le planning central, par exemple : `node scripts/prepare-order-data.mjs services 2026-10-28 35 > /tmp/forno-services.sql`. Contrôler puis exécuter le SQL dans Supabase. Les adresses `TODO_` deviennent NULL. Les services sont créés `scheduled`, commandes désactivées. Les créneaux utilisent les paramètres en base. Le script ne remplace jamais un service daté existant : une annulation ou une exception prévaut toujours.
4. Renseigner les vraies dates, lieux, adresses, horaires, capacités et fermetures avant activation. Les lignes datées **Supabase sont la seule autorité pour commander** ; le planning hebdomadaire `truckSchedule` est le modèle des passages habituels, sans repli automatique permettant de commander en l’absence d’un service en base. Un service fermé ne sera pas recréé par le générateur. Les indications publiques de planning habituel n’autorisent jamais une commande.
5. Configurer un widget Cloudflare Turnstile autorisant le véritable domaine du site. Les tokens sont validés côté serveur, avec contrôle du domaine et de l’action `order`. Ne pas utiliser les clés de test en production.
6. Définir **dans les secrets runtime Sites**, jamais dans Git ni dans une variable `PUBLIC_` : `SUPABASE_URL`, `SUPABASE_SECRET_KEY`, `ORDER_RATE_LIMIT_SALT` (au moins 32 caractères aléatoires), `TURNSTILE_SECRET_KEY`, `TURNSTILE_SITE_KEY` (clé de widget publique par conception). Pour le développement Cloudflare, utiliser `.dev.vars` ignoré par Git, en reprenant `.env.example`. Aucun secret n’est requis pour compiler le site. Redéployer après configuration des variables runtime.
7. Vérifier les migrations, les tests Supabase réels, les règles RLS via un client anonyme et le cron. Valider les vrais prix/planning et compléter la politique de confidentialité existante (responsable, hébergeurs, finalités, durée effective, droits et Turnstile). Le modèle juridique existant reste à compléter ; aucune identité ou base légale n’a été inventée.
8. Activer explicitement un service vérifié en base (`status='open'`, `orders_enabled=true`). `open` signifie ici « accepte des demandes » ; il peut être activé avant l’heure d’ouverture physique pour les retraits du soir. `scheduled` ne suffit jamais. Une fermeture/cancellation ou commandes désactivées interdit tout nouvel enregistrement. Aucun espace administrateur n’est fourni à cette étape.

Les valeurs opérationnelles sont dans `forno_private.settings` : préparation 30 min, marge de fermeture 15 min, intervalle 15 min, capacité initiale 8 **pizzas** par créneau, maximum 20 pizzas par demande, expiration pending 15 min, conservation technique 30 jours par défaut. Ce sont des paramètres initiaux à valider pour l’activité, pas des durées légales affirmées. Ne pas augmenter le maximum sans aligner le schéma de l’API, le panier et ses tests.

## API et transaction

- `GET /api/pickup-slots?quantity=N` : heure serveur, date Paris, service du jour uniquement, créneaux `available`, `full`, `unavailable`, sans aucune donnée client. Les complets sont visibles mais non sélectionnables. `quantity` mesure la charge du panier, pas le nombre de commandes. Refus fermé/désactivé/terminé, préparation minimum et disponibilité revérifiés au POST.
- `POST /api/orders` : schéma Zod strict, taille limitée à 16 Kio y compris en streaming, vérification des noms, téléphone français, quantités et unicité des lignes, origine de même domaine, Turnstile. Les prix/statuts/totaux fournis par le navigateur sont rejetés. Le serveur transmet seulement les lignes normalisées et une empreinte à la RPC protégée.
- `forno_create_order` s’exécute dans une transaction : verrou transactionnel d’idempotence, verrou du service, verrou du créneau, prix relus et verrouillés en base, capacité recalculée, insertion de la commande et des snapshots des lignes. Chaque contrôleur futur des statuts doit prendre le verrou du service avant celui du créneau et ne jamais ressusciter un pending expiré sans revérifier la capacité.
- La date réelle provient de l’horloge PostgreSQL convertie en `Europe/Paris`. Le service, sa date, son village, le créneau, les horaires et le délai sont revérifiés après les verrous. Aucun autre jour, y compris demain, n’est accepté. Le navigateur compare les dates renvoyées par l’API et demande une actualisation après minuit.
- Les prix sont exclusivement ceux de `pizzas` ; `order_items` conserve le nom et le prix au moment de l’achat. Une modification future du catalogue n’altère pas les snapshots. Les FK empêchent de supprimer un service, créneau ou produit utilisé ; supprimer explicitement une commande supprime ses lignes par cascade.
- Le bouton est verrouillé pendant l’envoi. Une même clé UUID v4 et une même demande produisent le même reçu ; une réutilisation avec des données différentes est refusée. L’empreinte exclut Turnstile, dont le token peut être renouvelé. En cas de panne réseau, la demande reste figée et les retours d’étapes sont désactivés jusqu’à résolution ; le même envoi peut être repris sans doublon.
- `GET /api/orders` avec l’en-tête `X-Order-Request-Key` permet de retrouver **uniquement le reçu sans coordonnées** associé à cette capacité UUID imprévisible, jamais une liste. Cette clé ne figure pas dans les URL. Le frontend conserve en session seulement cette clé et les quantités ; ni nom, ni téléphone, ni commentaire. Une actualisation récupère le résultat réel au serveur. Ce mécanisme n’est pas un compte client ni une interface de suivi public par numéro de commande.
- Le panier est décrémenté seulement après reçu serveur, à partir des quantités effectivement enregistrées, en préservant les ajouts intervenus entre-temps. La confirmation rappelle la référence, le statut réel, le lieu, l’heure, le total, le paiement au camion et l’échéance du pending. `pending` ne signifie jamais `accepted`.

## Capacité, expiration, confidentialité

Consomment la capacité : pending non expiré, accepted, preparing, ready, completed. Rejected/cancelled n’en consomment pas. L’unité est la **pizza** (somme des quantités). Le calcul des disponibilités ignore immédiatement un pending dont `pending_expires_at` est dépassé, même si le cron est retardé. `forno_maintenance` annule les pending expirés chaque minute via `pg_cron`. Vérifier régulièrement `cron.job_run_details` ; une demande acceptée doit être traitée avant son échéance. Le futur admin doit gérer explicitement ces états et ces verrous.

La maintenance purge nom, prénom, téléphone, note et empreinte de demande après `retention_days`, conserve uniquement les éléments de commande et la date de purge. Les journaux applicatifs ne contiennent ni corps de requête ni téléphone. Les compteurs anti-abus stockent seulement un HMAC d’IP et sont supprimés après 24 heures. La procédure de purge est `select public.forno_maintenance()` ; une suppression ciblée autorisée peut aussi anonymiser les colonnes correspondantes dans Supabase. Documenter séparément la politique de sauvegardes et les éventuelles obligations de conservation avant mise en service.

RLS est activé, sans politique client. Les privilèges de tables et d’exécution RPC sont retirés à `public`, `anon` et `authenticated`. Les RPC applicatives `security definer` utilisent un search_path vide et des tables qualifiées ; seul `service_role` peut les appeler via la Data API. Ce rôle ne possède aucun droit direct sur les tables FORNO. La maintenance n’est pas une capacité de la clé applicative et reste réservée au propriétaire SQL / cron. Aucune clé privilégiée n’atteint le navigateur. La future authentification administrateur nécessite ses propres contrôles d’identité et politiques : ne pas accorder l’accès aux commandes au rôle authenticated global.

Limitation de débit persistante en base (pas de compteur isolé en mémoire Worker) : 15 tentatives/minute/IP sur l’API de commande, 5 créations/minute/IP, 60 lectures/minute/IP des créneaux, plus Turnstile. La capacité reste transactionnelle même avec plusieurs Workers. La panne de l’un des contrôles bloque l’envoi.

## Vérifications

- `npm run test:checkout` : tests existants du panier, validation, planning du jour, fuseau Paris et changements d’heure.
- `npm run test:orders` : schéma et handlers, SQL exécuté dans PostgreSQL PGlite isolé, snapshots/prix, fermetures, idempotence, expiration, purge, capacités et RLS avec rôles anon/authenticated. Les horloges SQL sont remplacées **uniquement dans la copie de test**, jamais dans la migration de production. Turnstile et le transport Supabase sont injectés dans les tests ; cela ne constitue pas une connexion réelle au projet Supabase.
- PGlite utilise une seule connexion et met les appels concurrents en file. Il vérifie les résultats, mais **ne prouve pas les verrous entre deux connexions PostgreSQL indépendantes**. Le scénario `supabase/tests/concurrency.md` reste à exécuter sur une base de test Supabase/PostgreSQL, ainsi que l’extension pg_cron et un vrai jeton Turnstile.
- `npm run check`, `npm run build`, puis contrôles navigateur desktop/mobile. Le cas non configuré doit montrer une fermeture de l’envoi, jamais un succès de démonstration.

Sources officielles utilisées : [clés Supabase](https://supabase.com/docs/guides/getting-started/api-keys), [fonctions sécurisées](https://supabase.com/docs/guides/database/functions), [adapter Astro Cloudflare](https://docs.astro.build/en/guides/integrations-guide/cloudflare/), [validation serveur Turnstile](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/).
